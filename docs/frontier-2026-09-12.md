## The idle barrier is now proven to be a WORK-QUEUE futex, not a fixed token

Live-captured (JIT_THREADS with futex args in the snapshot, commit this cycle):
all 3 guest threads (tids 0,1,2) park at guest lr=0x10284d134 with

    x0=0x62(98)  x1=latch(uaddr=x19+4)  x2=0x89(FUTEX_WAIT_BITSET|PRIVATE)
    x3=0x0  x5=0x0(NULL uaddr2)  x6=bitset

So the waiter blocks while `*latch == 0x0` — the latch is re-armed to 0 each
cycle and only proceeds when a producer posts a NON-ZERO value (a work token).

**The `--futex-kick`/`--futex-set` host Kicker is therefore NOT a producer:**
- `--futex-kick 2` writes `old+1` (0→1): the futex returns, the engine does a
  tiny bit of work, re-arms the latch to 0, and re-parks. Compiles stay flat at
  1668 (StartApp init settled) / ~8713 hits.
- `--futex-set 0xf4240` (this cycle, NEW harness option): writes the exact
  token verbatim each tick; latch sticks at 0xf4240; compiles STILL flat at
  1668. A fixed token is not enough — the consumer checks something beyond the
  latch (a real queue/task structure) before doing work, so a bare futex poke
  can never advance it.

Conclusion: the engine's per-thread idle futex is a *signal*, not the *work*.
The producer must enqueue an actual unit of work (render/task) into the engine's
queue, then set the latch. That queue's structure lives in host-heap per-thread
objects (x19[*=0x0], latch uaddr = x19+4); reconstructing it requires reading
the consumer path after the futex returns (what it dequeues) — the frontier.
